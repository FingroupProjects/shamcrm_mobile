# ТЗ: переход на централизованную систему тем и цветовых ключей

## 1. Зачем это делаем

Сейчас в проекте цвета, шрифты, фоны, тени, границы и состояния компонентов заданы вручную во множестве файлов.  
Из-за этого добавление новых тем, смена палитры или даже простая правка одного цвета становится дорогой и рискованной задачей.

Цель: перейти на подход как у Telegram:

- все цвета живут только в одном месте;
- каждый цвет имеет понятный ключ;
- виджеты, экраны, поля, кнопки, тексты, иконки, тени и состояния не содержат прямых цветов;
- при добавлении новой темы меняются только файлы палитры, а весь UI обновляется через ключи.

Новая система должна разделять:

- палитру темы;
- семантические токены;

## 4. Главный принцип

### Запрещено в UI-слое

После миграции в экранах, виджетах и формах не должно быть:

- `Color(0x...)`
- `Colors.red`, `Colors.white`, `Colors.black` и т.д.
- локальных цветовых констант внутри экранов
- `fontFamily: 'Gilroy'` напрямую в виджетах
- одинаковых `TextStyle(...)`, скопированных по файлам

### Разрешено

В UI-слое должны использоваться только ключи:

- `context.appColors.textPrimary`
- `context.appColors.backgroundPrimary`
- `context.appColors.buttonDanger`
- `context.appTextStyles.bodyMd`
- `context.appTextStyles.titleLg`
- `context.appShadows.card`

## 5. Как строим цвета

### Уровень 1: сырая палитра

Это реальные hex-цвета темы:

- `primary500`
- `primary700`
- `neutral0`
- `neutral100`
- `success500`
- `warning500`
- `danger500`

Эти значения отличаются между темами.

### Уровень 2: семантические ключи

UI не должен знать про `primary500` напрямую.  
UI должен знать только назначение цвета:

- `backgroundPrimary`
- `backgroundSecondary`
- `surfacePrimary`
- `surfaceElevated`
- `textPrimary`
- `textSecondary`
- `textInverse`
- `iconPrimary`
- `iconSecondary`
- `borderPrimary`
- `borderSubtle`
- `buttonPrimaryBg`
- `buttonPrimaryFg`
- `buttonDangerBg`
- `fieldBg`
- `fieldBorder`
- `fieldHint`
- `shadowColor`
- `overlayColor`
- `success`
- `warning`
- `error`
- `info`

Именно эти ключи будут использовать все экраны.

---

## 6. Как строим шрифты

Нужно вынести шрифты так же, как цвета.

### Отдельно храним

- семейства шрифтов
- размеры
- веса
- высоту строки
- готовые текстовые стили

### Пример целевых ключей

- `displayLg`
- `titleLg`
- `titleMd`
- `bodyLg`
- `bodyMd`
- `bodySm`
- `labelLg`
- `labelMd`
- `caption`

Если у экрана есть цвет текста, он не задается внутри `TextStyle(...)` вручную.  
Цвет должен подмешиваться через тему или через семантический токен.

---

## 7. Обязательные правила миграции

### Правило 1

Сначала создаем новую theme-архитектуру, потом переносим папки по очереди.

### Правило 2

Сначала переносим общие переиспользуемые виджеты, потом экраны.

### Правило 3

Нельзя смешивать старый и новый подход в одном и том же общем компоненте.

### Правило 4

Все новые экраны и новые задачи уже пишутся только через новую тему.

### Правило 5

`AppColors` в `lib/utils/app_colors.dart` не расширяем бесконечно.  
Он должен либо стать адаптером к новой системе, либо быть удален после полной миграции.

## 8. Порядок работ по этапам

## Этап 0. Аудит и карта токенов

### Задача

Собрать все повторяющиеся цвета, стили текста, фоны, границы, тени, статусы.

### Что делаем

- собираем список всех прямых цветов в `lib/`;
- группируем одинаковые hex-цвета;
- определяем, какие из них брендовые, какие нейтральные, какие статусы;
- собираем повторяющиеся `TextStyle`;
- определяем базовые токены для текста, полей, кнопок, карточек, табов, алертов.

### Результат

- готовая карта палитры;
- список семантических токенов;
- список legacy-цветов, которые будут заменены.

## Этап 1. Базовый theme-core

### Папки

- `lib/core/theme/`

### Что делаем

- создаем палитры тем;
- создаем семантические color tokens;
- создаем typography tokens;
- создаем ThemeExtension или аналогичный механизм;
- создаем `ThemeData`, связанный с новой системой;
- подключаем новую тему в `lib/main.dart`.

### Результат

- приложение умеет получать цвета и стили из одной точки;
- появляется основа для нескольких тем.

## 9. Технические правила для команды

### Обязательный код-стандарт

Для всех новых PR:

- не использовать `Color(...)` в экранах и общих виджетах;
- не использовать `Colors.*` в UI, кроме очень редких технических случаев;
- не писать `fontFamily` вручную в экранах;
- не создавать локальные `TextStyle`, если стиль уже существует в токенах;
- не добавлять новый цвет без добавления ключа в theme-system.

### Исключения

Допускаются только:

- временный compatibility layer во время миграции;
- системные platform-specific цвета в `ios/`, `android/`, widgets/native;
- сторонние пакеты в `third_party/`, если мы их не переписываем прямо сейчас.

## 10. Definition of Done

Этап считается завершенным только если:

- в целевых папках больше нет прямых цветов в UI-коде;
- в целевых папках больше нет прямых `fontFamily`;
- все кнопки, поля, тексты, карточки и состояния берут стили из theme-system;
- экран визуально не сломан;
- светлая тема полностью работает;
- добавление второй темы требует изменения только palette/theme файлов.

## 13. Важное замечание

Сначала надо сделать не "новые красивые цвета", а "правильную систему ключей".  
Если сразу начать придумывать много тем без токенов и семантики, проект станет еще сложнее.

Правильный порядок такой:

1. единый theme-core;
2. light theme как эталон текущего дизайна;
3. полная миграция экранов на ключи;
4. только после этого добавление новых тем.
