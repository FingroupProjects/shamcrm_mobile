Сейчас точка остановки такая: в этой ветке у вас уже есть сильная iOS-заготовка, но она не доведена до production-схемы.

Фактически состояние проекта:
IOSNativeSipManager.swift уже реализует PushKit + CallKit + Linphone.
AppDelegate.swift подключает native SIP manager.
Info.plist содержит voip background mode.
Но в sip_service.dart iPhone до сих пор не переведён на native SIP как основной движок, потому что _shouldUseNativeSip() возвращает true только для Android UDP/TCP. То есть iOS сейчас живёт на sip_ua/flutter_webrtc, а native-часть используется лишь частично. Это главный блокер.

Второй важный факт: в version_5 этот iOS native SIP вообще был вырезан перед релизом. То есть вы остановились ровно перед этапом “сделать iPhone native-first и production-ready”.

Что нужно сделать по-настоящему
Если цель: “чтобы iPhone работал как телефон/WhatsApp, в фоне и при закрытом приложении”, то правильная цель не “держать SIP websocket/tcp/udp живым в фоне”, а такая:

Регистрация и входящий вызов в фоне идут через APNs VoIP Push + PushKit + CallKit.
После прихода push приложение быстро поднимает native SIP stack, принимает INVITE, показывает системный экран звонка.
После Answer звук и media полностью переключаются на native iOS audio session.
Flutter UI уже только отображает состояние и журнал, а не является критическим для доставки звонка.
При killed-state входящий звонок всё равно доходит через VoIP push.
Именно это на iOS реалистично. “Постоянно держать SIP как Android” на iPhone нельзя считать надёжной архитектурой: Apple это режет.

Идеальное ТЗ
Цель:
Реализовать production-grade iOS SIP телефонию уровня системного телефона: стабильный входящий вызов в foreground/background/terminated state, корректная работа CallKit, надёжная доставка через VoIP push, устойчивое восстановление регистрации, правильная маршрутизация аудио и минимальные пропуски звонков.

Функциональные требования:

Входящий звонок приходит при открытом, свёрнутом и убитом приложении.
На iPhone показывается системный экран CallKit с именем/номером.
Ответ с lock screen, Dynamic Island/Call UI и Bluetooth/гарнитуры должен работать.
После ответа вызов поднимается не через Flutter runtime как обязательную точку, а через native iOS SIP stack.
Исходящий звонок должен стартовать стабильно и быстро.
Завершение, decline, mute, speaker, audio route должны работать через native iOS layer.
VoIP token должен автоматически регистрироваться на backend и обновляться при изменении.
Если SIP account сохранён, приложение должно само восстанавливать готовность после перезапуска.
Должна быть защита от гонок: push пришёл раньше SIP registration, пользователь нажал Answer раньше INVITE, CallKit action пришёл раньше Flutter.
Должна быть диагностика по каждому звонку: push received, callkit shown, SIP invite received, answer action, media connected, end reason.
Нефункциональные требования:

Время от VoIP push до показа CallKit: до 2 секунд.
Время от Answer до audio connected: целевой коридор 1-3 секунды.
Missed-call rate в фоне должен быть минимальным и измеряемым.
Архитектура не должна зависеть от того, открыт ли Flutter экран SIP.
Любая критичная логика входящего звонка должна жить в native iOS слое.

Не пытаться добиться идеала через sip_ua в фоне на iOS.

Что сделал по Этапу 6:
В IOSNativeSipManager.swift onListen() теперь сразу отдаёт актуальные snapshot-события:

registration
call
pending_call_actions
app_visibility
audio_session
Это значит, что при позднем подключении Flutter event stream сервис не ждёт нового входящего звонка или нового route change, а сразу получает текущее native состояние.

В sip_service.dart добавил _resyncNativeBridgeState(), который после поднятия native bridge сам дотягивает:

текущий snapshot
pending iOS call actions
То есть позднее подключение Flutter теперь реально восстанавливает состояние, а не живёт на “что прилетит дальше”.
